# 04. 운영 알림 임계 (초안, 2026-11-25) — 12-02 관찰 종료 뒤 확정

docs/01 §6 "알림 임계: 1주차는 알림 없이 기준선만, 2주차에 분포로 임계(docs/54)". 임계는 사람이 고르는 숫자가 아니라 **관찰된 분포의 꼬리 밖**에 둔다. 아래 분포는 `mp2.ops_metrics_5m` 11-24 03:02 ~ 11-25 11:00 UTC(5분 버킷 381개, 약 32시간)이고, 7일 분포가 모이면 같은 쿼리로 다시 뽑아 숫자만 바꾼다. **이 문서는 설계만 적는다. 코드 적용은 관찰 종료 뒤.**

## 2. 임계 제안 — 분포 꼬리의 바깥, 그리고 "무엇을 잡으려는가"

| # | 신호 | 현재 규칙(health_check 10분) | 제안 | 분포 대비 | 잡으려는 사고 |
|---|---|---|---|---|---|
| A1 | 최근 10분 적재 0건 | critical | **유지** | 정상 최소 1,244행/5분(upbit/trades p05) — 0 은 10,000배 밖 | 수집기 정지, CH 적재 정지(#2 가 이걸로 잡혔다) |
| A2 | 표 신선도 (now − max recv_ts) | 없음 | **> 30초가 5분 버킷 2개 연속 → warning**, > 5분 → critical | p99 1.1초의 30배 | 배처가 느리게 막히는 중간 상태(#2 는 79분 뒤에야 0건이 됐다). A1 보다 먼저 울린다 |
| A3 | 수신 지연 lag p95 | 없음 | **> 3,000ms 가 3버킷 연속 → warning** | p99 406ms 의 7배, v1 합격선과 같은 3초 | 거래소 지연·호스트 과부하. 재접속 스냅샷 꼬리는 p95 라 안 걸린다 |
| A4 | 재접속·공백 | 1시간 ≥3회 또는 ≥300초 → warning | **≥3회/h 유지, 단일 공백 ≥120초 → critical 추가** | 관측 최대 5회/h·32초 | 재접속 폭주(백오프 상한 60초가 걸릴 때), 긴 끊김 |
| A5 | ClickHouse RSS | 없음 | **> 2,600MB(한도의 85%) → warning** | max 1,955(export 중) | 메모리 한도 사고(v1 ClickHouse 3번 상향의 재발 감지) |
| A6 | 디스크 | 여유 < 50GB warning, < 20GB critical | **"남은 일수" 로 바꾼다: 여유 ÷ 최근 7일 평균 일 증가량 < 14일 → warning, < 5일 → critical** | 일 증가 ≈ 11.4GB(원문 7.1 + Parquet 2.2 + CH 2.1) → 370GB 는 32일 | 보존 정책 미결 상태에서 디스크가 차는 것. GB 임계는 증가 속도를 모른다 |
| A7 | 거래소 대조 | dbt 테스트 셀 <99% → DAG 실패 → critical | **유지** + 일 가중 비율도 함께 기록 | 11-24 Upbit 84/12,611셀(재접속 공백), 가중 99.9% | 유실(#7 이 이걸로 드러났다) |
| A8 | export 셀 대조 | 불일치 → 태스크 실패 → Slack | **유지** | 11-25 4/4 일치 | 파서·파일·라이브 불일치 |
| A9 | `envelopes_rejected` 건수 | (브랜치 머지 전) | **> 0 → warning** | 0 | 모르는 schema_version/스트림(docs/03) |
| A10 | heartbeat(Oracle 감시자) | 12분 부재 → down, CH 못 읽음 → degraded | **유지** | 11-20 정전 때 01:45 감지 | 호스트·터널 사망 |

원칙: **같은 사고에 critical 은 하나만.** A1·A2 가 같은 사고(적재 정지)의 조기/확정 단계라 A2 는 warning, A1 이 critical. 알림 경로는 incidents 표에 먼저 쓰고 Slack 은 그 다음(11-25 #1·#8 처럼 발송이 깨져도 기록은 남게).
